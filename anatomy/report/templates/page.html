  • Bandwidth floor modelledThe step's bytes (weights once, every sequence's KV cache) over the card's measured streaming bandwidth (the fastest of a read, a copy and a GEMV at the locked clock). A reference for this card, not a physical limit for every access pattern.
  • Copies measuredMemory the GPU copies or sets outside any kernel: logits copied to the host for sampling, inputs copied in.
  • Kernel excess what remainsKernel time beyond the floor and the launch cost: kernels that do not stream memory at full speed.
  • Launch cost modelledWhat starting each kernel costs the GPU, even inside a CUDA graph: the kernels per step times what a graph node costs on this card (less what a launch hidden under the kernel before it saves), plus the gaps the traces show. What a megakernel removes.
  • Host stall measuredTime the GPU has nothing to do because the host has not sent the next step yet.

Modelled parts rest on a model (bytes per step; kernels times the node cost the ruler measured), so they carry its assumptions; the measured ones come straight from the traces. The parts add up by construction, which checks the arithmetic, not the causes: switching one mechanism off at a time (below) is what tests them.

{{ titles.calculator }}

A scenario, not a measurement. Each engine's host cost per step is fitted from the measured cells (a fixed part plus a part per sequence); with the bytes' share of the GPU's time scaled by another card's memory bandwidth, and everything else held as measured here (the same host CPU, kernels, graph-node cost and clocks), it shows where the crossover would land. Another card changes more than its bandwidth, and no measurement on one has tested this yet: read it as a what-if with the band of the fit's own uncertainty, not as a forecast.

Any engine, model and batch at its default settings, accepted or not: what was measured, every check it passed or failed, where its raw files are, and how to measure it again. The address keeps the choice, so a cell can be linked.

How it is measured

Step time comes from unprofiled runs: every output token is timestamped as it arrives, and the step is the time per token while all sequences of a batch are decoding together. It must agree within 3% with an independent estimate from two runs that differ only in output length, each timed from every stream's first token to its last and compared over the same tokens.

Repeats inside one process need not bound the spread between separate processes of the same cell, so the first session runs cells of every engine (two model sizes, three batch widths, one setting that leaves the GPU waiting on the host) as separate processes at its start and end. A difference between cells counts only beyond {{ times }} that noise, and cells compared with each other run back to back in one session.

GPU busy is the share of a step the GPU has work in flight (kernels, copies, graph launches), from Nsight Systems: not CUDA's occupancy (warps resident per multiprocessor), and not nvidia-smi's utilisation, which counts any time a kernel ran. Busy time and kernel time come from separate captures of the same cells: busy time from a low-overhead trace that sees each CUDA graph as one block, kernel time from a trace that sees every kernel inside the graphs. Tracing slows the host but not the GPU's work, so the busy share is the GPU's busy time per step in the trace over the step time of the unprofiled run; a trace whose GPU work does not fit in that step is rejected.

The server's step against the engine API's is the whole stack's difference (HTTP, streaming, detokenising, the server's own scheduling), not the cost of HTTP alone.

Before any engine was measured, the trace parser was checked against a synthetic workload with a known busy fraction, and the card's achievable bandwidth was measured, so "speed of light" means this card, not the datasheet.

What checking the harness changed

  • CUPTI counts a kernel's launch inside its duration, so the gaps between kernels read near zero and launch cost hid in kernel excess: the launch term counts kernels at the card's measured graph-node cost.
  • Tracing stretches a host-bound step (SGLang's batch 1 by 4%), so the busy share is busy time over the unprofiled step, and contending the host's cores tests that the GPU's work did not move.
  • A graph launch that missed the step where an engine's KV view grows, and a prefill graph that outnumbered decode's at 256 sequences: each engine's step is anchored on its own once-a-step event, and a missed one rejects the window.
  • SGLang admitted 255 of 256 sequences, its chunked request counted twice: a batch that never ran whole is rejected and says so.

Every failure the harness now catches, and what catches it, is in the repository's validation record.
